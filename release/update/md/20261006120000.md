# v1.0.4.2 · 云端 CI 自动构建流水线

`v1.0.4.2` · 重大新增功能 · 发布：2026-10-06 12:00:00 · 作者：AtomCode

本版引入 **GitHub Actions 云端自动构建流水线**，把「构建」从贡献者的电脑搬到云端。
贡献者现在可以完全不配置本地环境，直接在线提交修改，云端自动完成全部构建校验与部署。

> **【重要声明 · 预发布版本】**
>
> 当前这套 CI 云端构建系统属于**预发布版本**，**系统不稳定，仍需要长期测试、反复迭代修改与校验实际输出内容，不保证输出结果完全无误**。现阶段依然**优先推荐本地构建方式**。用户可以自行修改、调试这套流水线相关配置用于测试。

---

## 一、版本概述

本版为**工程能力版本**，不改动站点内容与导航，核心是新增一套云端 CI 流水线，并由此形成两套并行的贡献方案。

**原有模式**：全部贡献者必须本地搭建环境——安装 Python、安装锁定版本的 MkDocs 与 Material 主题、克隆仓库，改完后还要本地 `mkdocs build` 自检，确认无报错才敢提交。

**新模式**：贡献者**可选**本地构建，也**可以完全不配置本地环境**，直接在线提交修改，云端自动完成全部构建校验。

相比旧的纯本地自构建模式，本流水线**大幅降低了贡献门槛**：

| 收益 | 说明 |
|---|---|
| 省去本地安装依赖 | 不必装 Python、MkDocs、Material 主题，也不必处理 PEP 668 之类的环境问题 |
| 节省本地算力 | 一次全站构建约 850 秒，风扇转满、机器发烫；云端构建不占用贡献者机器 |
| 降低新手学习成本 | 不必先学会一整套工具链，才能改一个错别字 |

## 二、两套触发逻辑

同一份配置 `.github/workflows/docs-ci.yml` 承担两种职责，按事件类型区分：

| 触发事件 | 执行内容 | 是否部署 |
|---|---|---|
| **Pull Request → main** | 仅执行构建校验（`mkdocs build --strict`） | **不部署**，只给出检查结果 |
| **Push / 合并 → main** | 构建校验，通过后自动部署静态站点到 GitHub Pages | **自动部署** |

**PR 阶段不部署**，是为了让尚未经过审核的内容不会意外上线。构建失败会以红色叉号显示在 PR 上，配合分支保护规则即可**阻止合并**，从机制上避免把构建不过的改动并进主分支。

**合并后才部署**，是为了让「合并」与「上线」成为同一个动作，不出现主分支内容与线上不一致的中间状态。

## 三、流水线执行内容

流水线不只是跑一句 `mkdocs build`，依次完成：

1. **检出仓库**，保留完整 git 历史（站点地图需要提交时间作为 `lastmod`）
2. **安装锁定版本环境**：`mkdocs==1.6.1` 与 `mkdocs-material==9.7.7`，并**主动核对版本号**，不一致立即失败
3. **严格构建**：`mkdocs build --strict`，任何警告都视为失败
4. **统计产物**：输出页面数与产物体积，便于比对
5. **修正站点地图**：剔除 MkDocs 自动生成的 sitemap，落回本站定制版
6. **核对 sitemap 收录情况**（仅提示，不阻断）
7. **叠加仓库独有文件**：`CNAME`、`BingSiteAuth.xml`、`data/`、`release/update/` 子站数据、`img/user/` 头像资源等构建不会生成、但线上必须存在的文件
8. **上传产物**：PR 阶段作为可下载的校验产物，push 阶段作为 Pages 部署产物

> **版本锁定不可放松**。不同版本的 MkDocs / Material 会改变生成的页面结构、`meta generator` 与页眉页脚。流水线主动核对版本，正是为了保证云端产物与线上逐字一致。

## 四、两套贡献方案

### 方式 A：云端自动构建（轻度贡献可选，预发布测试状态）

**适合**：偶尔改几个错别字、补一段说明、修一个失效链接的轻度贡献者；电脑上没有环境、装不上 Python、或不愿意为此折腾的成员；只想专注写作、不想碰工具链的新手。

**流程**：在线编辑 Markdown / SVG → 提交 PR → 云端自动构建校验 → 通过显示绿色对勾（可下载产物预览）、失败显示红色叉号并指出报错位置 → 修正后重新提交 → 审核合并 → 自动部署上线。

**局限**：受预发布状态影响，云端构建结果**不保证完全可靠**，偶尔可能出现环境差异导致的失败或输出偏差。

### 方式 B：本地自构建（现阶段优先推荐）

**适合**：需要频繁改动、要调导航与主题配置、或对产物正确性要求较高的成员；以及希望改动在提交前就确认无误的谨慎型贡献者。

**流程**：本地装好锁定版本环境 → `mkdocs serve` 实时预览 → 提交前 `mkdocs build --strict` 自检 → 提交 PR → 云端流水线同样跑一遍校验作为双重保险 → 合并后自动部署。

**优势**：反馈最快、结果最确定，构建版本与线上严格一致。
