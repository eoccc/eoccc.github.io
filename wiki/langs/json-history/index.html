    JSON 的发展历程与现代前景

    本页讲述 JSON 从何而来、为何能成为事实标准，以及它在今天的地位与未来走向。

    一、发展历程

    1. 前身：JavaScript 对象字面量

    JSON 的语法并非凭空设计，而是直接取自 JavaScript 的对象字面量写法。在 1990 年代末，这种「用花括号写数据」的形式已经在 Web 前端广泛使用。

    2. 定型：2001 年前后

    Douglas Crockford 等人意识到，这种写法可以剥离掉 JavaScript 的语言特性（函数、undefined、注释等），只保留纯数据部分，从而得到一种极简的、语言无关的数据交换格式。随后注册 json.org 网站进行推广。

    3. 标准化进程

    时间 里程碑 意义
    2006 RFC 4627 首个正式规范，规定顶层必须是对象或数组
    2013 ECMA-404 给出语言无关的语法定义，不再依附于 JavaScript 规范
    2014 RFC 7159 放宽顶层值限制，任何 JSON 值都可作为顶层
    2017 RFC 8259 现行标准，同时被采纳为互联网标准 STD 90

    命名由来：JSON = JavaScript Object Notation（JavaScript 对象表示法）。名字里有 JavaScript，但它不属于 JavaScript——它是一种独立的文本格式。

    4. 为什么能取代 XML

    在 JSON 普及之前，XML 是数据交换的主流。二者对比如下：

    维度 XML JSON
    语法体量 标签、属性、DTD/Schema，规则繁多 仅对象与数组两种容器
    冗余程度 开闭标签成对出现，体积大 无冗余标签
    解析难度 需完整 XML 解析器 解析器实现极简
    与编程语言的映射 需额外约定 天然对应对象与数组

    JSON 语法极小、人类可读、解析器易于实现，在 Web API 与配置领域迅速成为事实标准。

    二、现代前景

    1. 依然是主流

    JSON 至今仍是数据交换与配置文件的「最小公约数」。只要两端需要一种都认识、都容易解析的格式，JSON 通常就是默认答案。

    2. 生态持续加深

    围绕 JSON 已经形成完整的技术栈：

    方向 代表规范 / 工具
    结构校验与文档 JSON Schema
    定位与取值 JSON Pointer
    增量变更 JSON Patch、JSON Merge Patch
    查询 JSONPath、JMESPath
    数据库存储 PostgreSQL jsonb、MongoDB 文档模型

    3. 短板与方言

    标准 JSON 的严格限制，在手写配置时很不方便：

    • 不允许注释
    • 不允许尾随逗号
    • 键名必须加引号
    • 不支持多行字符串

    于是出现了多种方言：

    方言 放宽之处
    HJSON 注释、无引号键名、省略逗号、多行字符串
    JSON5 注释、尾随逗号、单引号、十六进制数
    JSONC 注释（VS Code 配置常用）

    它们的共同思路是——在保持数据模型不变的前提下放宽书写规则。本站讲解的 HJSON 正是这一思路的产物。

    4. 竞争与替代

    格式 优势 局限
    YAML 可读性强、支持注释与锚点 缩进敏感、规则复杂、易踩坑
    TOML 面向配置、语义清晰 嵌套深时啰嗦
    MessagePack / CBOR 二进制、体积小、解析快 不可直接阅读

    在性能敏感场景，二进制格式会取代 JSON；但在配置与 API 领域，JSON 的地位短期内难以动摇。

    5. 在游戏与模组领域

    Mindustry 等内容驱动的游戏普遍以 JSON 描述内容定义，再以 HJSON 之类的方言提升手写体验。因此理解 JSON，实质上是理解这类游戏数据层的通用语言。

    三、小结

    结论 说明
    出身 从 JavaScript 语法中提炼，但语言无关
    地位 Web API 与配置的事实标准（STD 90）
    优势 语法极小、可读、解析器易实现、生态完整
    短板 不支持注释与尾随逗号，手写不便
    应对 HJSON、JSON5 等方言在数据模型不变的前提下放宽书写
    趋势 配置与 API 领域长期主流；性能场景让位于二进制格式
